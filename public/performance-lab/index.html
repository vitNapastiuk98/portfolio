Workload and measurement limits

Baseline delays the main content by 800 ms, does not reserve its space, and processes work in one task. Optimized renders it immediately, reserves space, and yields between chunks. Both calculate the same checksum.

This isolated HTML fixture uses the portfolio’s fonts and visual styling, but excludes Angular and the portfolio shell. Local LCP and CLS are lab observations. A scripted click is not field INP, and completing the background work can take longer when it yields.

From symptom to solution

What changed, and why?

Try the workspace above, then follow the code. These are three separate problems with three separate fixes.

01 / Content arrival

Show useful content sooner.

Try it: switch to Baseline and press “Replay content arrival”. The order panel disappears for 800 ms. In Optimized, it is available immediately.

The fix: remove the artificial wait. In a real application, avoid gating the main content on unrelated work. This does not make a required data request disappear.

Investigate with LCP · inspect the actual largest element

Baseline / unnecessary delay

// The data is ready, but the UI waits.
setTimeout(reveal, 800);

Solution / render when ready

// No artificial gate before rendering.
reveal();

02 / Layout stability

Keep the action in place.

Watch Save report: in Baseline, the panel arrives above it and pushes it down. The optimized slot reserves room instead of growing from nothing.

The fix: give delayed content a predictable footprint. For images, provide width and height or an aspect ratio. Match reserved space to the content and viewport.

Investigate with CLS · replays after input may be excluded

Baseline / no reserved space

.content-slot {
  /* Hidden content occupies no space. */
  min-height: 0;
}

Solution / reserve the footprint

.content-slot {
  min-height: 260px;
}
@media (max-width: 480px) {
  .content-slot { min-height: 320px; }
}

03 / Main-thread work

Let the browser respond.

Press Save report: both modes calculate the same checksum over 30 million items. Baseline runs one uninterrupted loop. Optimized yields between chunks so the browser can show “Saving…” and progress.

The tradeoff: yielding can improve feedback while making total completion slower. On a fast device the difference may be subtle; the repeatable runner uses 4× CPU slowdown.

Investigate with an interaction trace · this demo does not measure field INP

Baseline / one blocking task

feedback.textContent = 'Saving…';
for (let i = 0; i < count; i++) {
  checksum += Math.sqrt(i) * (i % 17);
}
feedback.textContent = 'Saved';

Solution / yield between chunks

for (let start = 0; start < count;
     start += chunkSize) {
  await new Promise(r => setTimeout(r, 0));
  const end = Math.min(start + chunkSize, count);
  for (let i = start; i < end; i++) {
    checksum += Math.sqrt(i) * (i % 17);
  }
}
